# Railway Deployment Guide for BadBlue

## Overview
This guide explains the Railway-specific configurations and fixes applied to ensure BadBlue runs reliably on Railway's production environment.

## Automatic Railway Detection
The system automatically detects Railway deployment through environment variables:
- `RAILWAY_ENVIRONMENT=production`
- `RAILWAY_PROJECT_ID` (any value)

## Database Configuration Adjustments

### For Railway Production
When deployed on Railway, the database connection automatically adjusts:

1. **Connection Pool Settings**:
   - Max connections: 20 (reduced from 100)
   - Min connections: 2 (reduced from 10)
   - Connection timeout: 30 seconds (increased from 10)
   - Statement timeout: 30 seconds
   - Query timeout: 30 seconds

2. **SSL Configuration**:
   - Automatically detects and applies SSL settings
   - Supports custom SSL certificates via `DATABASE_SSL_CERT` env variable

3. **Application Name**:
   - Sets `application_name: 'badblue-railway'` for monitoring

## BadBlue Worker Adjustments

### Railway-Specific Worker Configuration
1. **Database Heartbeat**:
   - Runs every 5 minutes (vs 15 minutes on standard)
   - 20-second timeout for queries (vs 10 seconds)
   - Requires 5 consecutive failures before repair (vs 3)
   - Initial delay of 30 seconds on startup

2. **Disabled Features in Railway**:
   - Autonomous search controller (to preserve API quotas)
   - 6-hour diagnostic cycles
   - Daily repair cycles
   - Weekly system tests
   - Weekly backups

3. **Graceful Shutdown**:
   - Handles SIGTERM signals from Railway
   - Waits up to 5 seconds for operations to complete
   - Cleans up all intervals and timers

## CRITICAL: Supabase IPv6 Fix

Railway's shared network does **NOT** support IPv6 egress. Supabase endpoints (including Session Pooler) return dual-stack DNS with IPv6 preferred. This causes `ENETUNREACH` errors.

### The Fix
Add this environment variable in Railway:

```env
NODE_OPTIONS="--dns-result-order=ipv4first"
```

This makes Node.js prefer IPv4 addresses in DNS resolution, which happens **before** the database client connects.

### Why Other Fixes Don't Work
- **pg Pool's `lookup` option**: Runs too late - DNS resolution already completed
- **Session Pooler (port 5432/6543)**: Still dual-stack, prefers IPv6
- **Custom DNS code**: Doesn't intercept Node's DNS at the right layer

## Migration Bundling Architecture

### The Problem
The build process uses `esbuild` to bundle `server/index.ts` into a single `dist/index.js` file. Originally, migrations were loaded via **dynamic imports**:
```typescript
await import(migration.module); // esbuild can't analyze variable-based imports
```

This caused `ENOENT: no such file or directory 'dist/migrations/...'` errors in production because esbuild couldn't include files referenced by dynamic string paths.

### The Solution
Migrations are now **statically imported** at the top of `server/index.ts`:
```typescript
import { createCoreTables } from "./migrations/createCoreTables";
import { createSubAgentTables } from "./migrations/createSubAgentTables";
// ... all 8 migrations
```

The `runMigrations()` function uses these static references directly:
```typescript
const migrations = [
  { name: 'Core tables', fn: createCoreTables },
  { name: 'Sub-Agent tables', fn: createSubAgentTables },
  // ...
];
```

This ensures esbuild bundles all migration code into the single `dist/index.js` file (~686KB).

## Deployment Steps

1. **Create Railway Project**:
   ```bash
   railway login
   railway init
   ```

2. **Add PostgreSQL Database**:
   - In Railway dashboard, add PostgreSQL plugin
   - Railway will auto-set DATABASE_URL

3. **Set Environment Variables**:
   ```bash
   railway variables set STRIPE_SECRET_KEY=sk_live_...
   railway variables set VITE_STRIPE_PUBLIC_KEY=pk_live_...
   railway variables set GEMINI_API_KEY=...
   railway variables set GROQ_API_KEY=...
   ```

4. **Deploy**:
   ```bash
   railway up
   ```

## Monitoring

### Check Deployment Status
- Railway Dashboard → Logs tab
- Look for: `[DATABASE] Connection pool created - ready for queries (Railway mode)`
- Worker should show: `[BadBlue Worker] Running in Railway production environment`

### Expected Log Messages
```
[DATABASE] Connection pool created - ready for queries (Railway mode)
[BadBlue Worker] Running in Railway production environment - adjusted settings applied
[BadBlue Worker] Skipping autonomous search controller in Railway environment
[BadBlue Worker] Heavy background tasks disabled in Railway environment
[BadBlue Worker] - Environment: Railway Production
[BadBlue Worker] - Database heartbeat: Every 5 minutes
```

### Database Connection Issues
If you see database heartbeat failures:
1. Check DATABASE_URL is set correctly
2. Verify PostgreSQL plugin is active
3. The system will auto-retry with timeouts
4. After 5 failures, auto-repair will trigger

## Troubleshooting

### Issue: Database Connection Failures
**Symptoms**: `Database heartbeat failed` in logs

**Solution**: 
- Verify DATABASE_URL environment variable
- Check Railway PostgreSQL plugin status
- System auto-recovers after temporary issues

### Issue: SIGTERM Signals
**Symptoms**: App receiving termination signals

**Solution**:
- Normal during Railway deployments
- App handles gracefully with 5-second shutdown window
- No action required

### Issue: High Memory Usage
**Symptoms**: Memory limits exceeded

**Solution**:
- Database pool is already optimized (20 connections max)
- Worker heavy tasks are disabled
- Consider upgrading Railway plan if needed

## Performance Optimization

### Railway-Specific Optimizations Applied
1. **Reduced database pool size** to work within Railway's proxy limits
2. **Disabled heavy background tasks** to reduce resource usage
3. **Optimized heartbeat intervals** for Railway's infrastructure
4. **Graceful shutdown handling** for smooth deployments
5. **Extended timeouts** for Railway's network topology

### Resource Usage
- Memory: ~200-400MB typical usage
- CPU: Low usage with worker optimizations
- Database connections: Max 20 (Railway-friendly)
